## 1. 连续非工作时间抵扣休息

### 1.1 恢复既定业务口径

美容师在两段工作之间的午休、请假、下班及其他连续非工作时间，都可以满足必要休息，不重复叠加，也不要求前台额外登记 `personal_rest`。

培训、准备、服务、整理、会议和值班属于工作。即使这些记录位于午休、请假或下班区间内，其覆盖时间也不能计入纯休息。

| 时间来源                      | 是否阻止新增工作 | 是否计入连续非工作时间 | 数据来源                                         |
| ----------------------------- | ---------------- | ---------------------- | ------------------------------------------------ |
| `meal_break`                  | 是               | 是                     | 已发布餐休                                       |
| `leave`                       | 是               | 是                     | 已生效请假                                       |
| `personal_rest`               | 是               | 是                     | 可选的明确休息，不是请假的附加登记               |
| `off_shift`                   | 是               | 是                     | 由已发布排班的上下班边界推导，不另建 restriction |
| `training`                    | 是               | 否                     | 已发布培训，属于工作                             |
| `preparation/service/cleanup` | 是               | 否                     | 计划占用或实际事实，属于工作                     |
| `meeting/on_duty`             | 是               | 否                     | 其他已发布工作安排                               |
| `manual_block`                | 是               | 否                     | 语义未知时只阻止接单，不推断休息                 |
| `equipment_fault`             | 是               | 不适用                 | 设备状态不能证明人员休息                         |
| `store_closed`                | 是               | 不单独证明             | 仍需结合员工排班和实际工作判断                   |

### 1.2 下班时间进入计算

每名美容师的已发布排班生成带门店时区的 `work_shift_period`。`off_shift` 是相邻已发布班次之间、不属于工作班次的时间区间，只参与计算，不要求操作人员登记。

例如，服务及整理在 21:50 结束，班次 22:00 结束，下一项工作在次日 10:00：若 21:50 后没有培训、会议或其他实际工作，则休息从 21:50 连续计算，经过 22:00 时不清零。必要休息为 30 分钟时，22:20 已满足。

若实际服务延长至 22:15，则下班边界不会覆盖实际工作，休息从 22:15 才开始。

### 1.3 计算规则

对服务 A 之后的最低休息，使用 A 创建时保存的规则快照：

1. 起点是 A 的实际工作结束；尚未发生时使用计划的整理结束；
2. 终点是下一项工作的准备开始；
3. 将其中已发布或已发生的培训、会议、值班、准备、服务、整理及其他工作区间取并集；
4. 候选休息是起终点之间扣除工作并集后的连续区间；午休、请假和下班只用于保证对应区间不会被分配新工作，不额外增加分钟；
5. 必须存在一段从最近一次工作结束后开始的连续非工作区间，长度达到最低休息分钟数；
6. 午休、请假和下班相邻或重叠时按并集处理，不重复累计，也不在边界处重新计时；
7. 任何培训或实际工作插入都会截断连续休息，之后重新计时。

因此，请假覆盖必要休息时直接满足，不需补录；休息从班内延续到下班后时连续计算；培训覆盖其中一段时必须扣除并按连续性重新判断。

## 2. 突发事实与普通计划调整分流

### 2.1 先判断变更模式

限制记录必须带来源模式，不能只按 restriction 类型决定处理方式：

| 模式             | 典型场景                                       | 生效原则                                       |
| ---------------- | ---------------------------------------------- | ---------------------------------------------- |
| `emergency_fact` | 美容师突然请假、临时无法到店、设备突然故障     | 真实事实立即保存并生效，之后处理受影响接待     |
| `planned_change` | 移动餐休、新增培训、调整未来排班、预先申请休假 | 先生成草稿和冲突预览；存在未处理冲突时禁止发布 |

同一个 `leave` 类型既可能是提前计划，也可能是突发事实，必须由业务入口和操作权限确定模式，不能靠操作人员随意把普通调整标成突发以绕过冲突检查。突发入口记录原因、操作者和审计事件。

### 2.2 突发事实处理

突发事实事务先取得完整预约锁，再保存事实并按以下规则处理：

| 相交情况                           | `held` 待确认申请                          | `confirmed` 已确认接待                             |
| ---------------------------------- | ------------------------------------------ | -------------------------------------------------- |
| 突发请假与准备、服务或整理相交     | 整组立即失效并释放全部资源，不尝试自动换人 | 保留原承诺和原分配，生成需要人工联系顾客的冲突待办 |
| 突发设备故障与对应资源工作片段相交 | 整组立即失效并释放，不自动换房或换床       | 保留原承诺，生成冲突待办                           |
| 请假仅覆盖必要休息                 | 兼容，申请保持有效                         | 兼容，不生成冲突；该时间可满足休息                 |

即使此时另有空闲美容师，旧预占也不会自动转给其他人。顾客或前台需要重新选择并明确确认新的人员、时间和报价，生成新的候选或改期操作。

多人接待中任何必要资源被突发事实击中时，待确认接待按整组失效，不能只保留部分顾客占用。

### 2.3 普通计划调整

普通计划调整只写草稿，不立即写入有效限制集合。发布事务在锁内重算全部相交记录：

- 与 held 或 confirmed 的准备、服务、整理不兼容：返回 `409 SCHEDULE_CHANGE_CONFLICT`，保持原已发布版本，返回冲突接待、片段和处理入口；
- 培训覆盖必要休息并导致连续休息不足：同样阻止发布；
- 移动餐休但仍完整覆盖必要休息，且不撞工作片段：兼容，可以发布；
- 所有冲突已由有权限人员明确改期、取消或调整计划后，重新校验无冲突才发布；
- 发布过程不自动更换美容师、房间、床位或修改顾客可见方案。

计划调整失败时，运营人员看到的是“哪些安排需要先处理”，而不是调整已经生效后才出现待办。

## 3. 阶段 0 前端错误处理

API 客户端使用 `ApiRequestError` 保留 HTTP 状态、业务错误码、请求 ID 和详情。工作台按以下状态呈现：

| 结果           | 管理后台行为                                                             |
| -------------- | ------------------------------------------------------------------------ |
| 200            | 展示今日工作台                                                           |
| 401            | 会话无效，跳转登录页                                                     |
| 403            | 留在工作台，显示“当前账号没有工作台权限”和“联系店长分配权限”，可切换账号 |
| 网络错误或 5xx | 留在工作台，显示服务暂不可用及“重新加载”按钮                             |

页面不再通过错误文案猜状态，也不会把 403 或系统故障重定向为重新登录。

前端单元测试验证：API 错误状态和业务码不会丢失；仅 401 返回登录动作；403 返回权限指引；网络错误和 500 返回重试动作。

## 4. 集成测试数据所有权

`operations.overview.read` 是固定权限目录项，不属于某一次测试运行。授权集成测试可以使用 `ON CONFLICT DO NOTHING` 保证它存在，但清理阶段绝不删除该权限。

测试只删除用本次随机后缀创建且已记录 ID 的会话、角色分配、角色、员工和门店。清理结束后重新查询并断言固定权限仍存在。因此，无论该权限是测试前已有还是本轮首次补齐，测试都不会删除它。

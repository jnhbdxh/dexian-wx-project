## 1. 限制类型与纯休息

### 1.1 固定语义，不由操作人员任意勾选

`resource_restrictions.type` 使用有限枚举。是否阻止接单、是否属于工作、是否能证明纯休息由服务端随类型固定，不能让前台自由组合布尔值。

| 限制类型               | 阻止新增预约 | 属于工作 | 可证明美容师纯休息 | 说明                                     |
| ---------------------- | ------------ | -------- | ------------------ | ---------------------------------------- |
| `meal_break`           | 是           | 否       | 是                 | 明确安排的用餐休息                       |
| `personal_rest`        | 是           | 否       | 是                 | 明确安排且无其他工作的休息               |
| `leave`                | 是           | 否       | 否                 | 人员不在岗，但不据此推断已满足接待间休息 |
| `training`             | 是           | 是       | 否                 | 培训属于工作                             |
| `store_closed`         | 是           | 不适用   | 否                 | 门店范围限制，不能证明某位员工在休息     |
| `equipment_fault`      | 是           | 不适用   | 否                 | 仅说明设备不可用                         |
| `manual_block`         | 是           | 未知     | 否                 | 原因未结构化时采用保守规则               |
| `post_service_cleanup` | 是           | 是       | 否                 | 实际服务结束后由系统生成的整理或床房清洁 |
| `required_rest`        | 是           | 否       | 是                 | 实际服务结束后由系统生成的美容师必要休息 |

`leave` 若确实包含可证明的休息，必须另外登记相交的 `personal_rest`；系统不从请假原因文字猜测。

### 1.2 占用阶段和兼容矩阵

计划占用至少区分 `preparation`、`service`、`cleanup`、`required_rest` 四种片段。限制保存后，只处理不兼容的相交，不以“有任何重叠”作为整组失效条件。

| 限制与计划片段                                                 | `held`                                               | `confirmed`                                    |
| -------------------------------------------------------------- | ---------------------------------------------------- | ---------------------------------------------- |
| `meal_break/personal_rest` 与 `required_rest`                  | 兼容，预约保持有效                                   | 兼容，不生成冲突待办                           |
| `meal_break/personal_rest` 与准备、服务或整理                  | 整组重新分配；无法满足时整组失效                     | 保留原承诺，生成冲突待办                       |
| `leave/training/manual_block` 与准备、服务或整理               | 整组重新分配；无法满足时整组失效                     | 保留原承诺，生成冲突待办                       |
| `training/manual_block` 与 `required_rest`                     | 原休息片段不再计入休息，重新计算；无法补足时整组失效 | 原休息片段不再计入休息；无法补足时生成冲突待办 |
| `leave/store_closed/equipment_fault` 只与 `required_rest` 相交 | 不单独判冲突，但这些限制不贡献休息分钟               | 不单独判冲突，但这些限制不贡献休息分钟         |

房间、床位和设备没有“个人纯休息”概念，只判断资源是否可用及清洁是否完成。

### 1.3 纯休息计算

美容师在服务 A 与下一项工作 B 之间的有效纯休息，按以下规则计算：

1. 从 A 的实际结束或尚未发生时的计划结束开始；
2. 取 `required_rest` 计划片段、`meal_break`、`personal_rest`、已发生的实际休息事实的并集；
3. 从并集中扣除培训、准备、服务、整理和其他实际工作事实覆盖的时间；
4. 结果必须存在一段连续区间，长度达到该次服务快照保存的最低休息分钟数；
5. `leave`、`store_closed`、`equipment_fault` 和 `manual_block` 不贡献纯休息分钟。

因此，午休覆盖原必要休息时预约保持有效；培训覆盖同一区间时，该段不能用于证明休息已经完成。

## 2. 实际事实、计划替代和更正链

### 2.1 稳定事实系列

同一项可更正事实使用一条稳定的 `resource_actual_fact_series`：

```text
id
store_id
reception_id
reception_guest_id
resource_id
fact_type
planned_allocation_id nullable
current_fact_id nullable
version integer
```

每一版内容写入 `resource_actual_facts`：

```text
id
series_id
version
actual_period
supersedes_fact_id nullable
recorded_by
correction_reason nullable
created_at
```

数据库约束：

- `UNIQUE(series_id, version)`；
- `UNIQUE(supersedes_fact_id) WHERE supersedes_fact_id IS NOT NULL`，一个事实最多只有一个直接后继；
- `(series_id, supersedes_fact_id)` 复合外键保证前驱属于同一系列；
- 系列表保存门店、接待、顾客、资源和事实类型，版本行不能改变这些主体；
- `planned_allocation_id` 必须属于同一门店、接待、顾客和资源；
- 当前有效事实只读取 `series.current_fact_id`，不再依靠“遍历后猜最后一条”。

### 2.2 并发更正

更正请求必须携带 `expectedVersion`。事务锁定事实系列后执行：

```sql
UPDATE resource_actual_fact_series
SET current_fact_id = :new_fact_id,
    version = version + 1
WHERE id = :series_id
  AND version = :expected_version;
```

更新影响 0 行返回 `409 FACT_VERSION_CHANGED`，同时回滚新版本。唯一后继约束是数据库兜底；系列版本是正常并发控制路径。两名前台不能产生两个有效事实头。

### 2.3 实际服务结束后的原子更新

记录或更正实际服务结束时间时，在同一事务中：

1. 锁定完整日期范围和接待组；
2. 写入新的实际事实版本；
3. 将被替代的本接待计划服务片段标为 `fulfilled`，将尚未发生的旧整理和休息片段标为 `superseded_by_fact`；历史记录不删除；
4. 使用接待创建时保存的准备、整理、清洁和休息规则快照，从实际结束时间重新计算后续影响；
5. 为美容师生成 `post_service_cleanup` 和 `required_rest` 系统限制，为房间、床位生成对应 `post_service_cleanup` 系统限制；
6. 每条系统限制保存 `source_fact_series_id` 和 `source_fact_version`。事实更正时，旧版本衍生限制标为 superseded，并原子写入新版本限制；
7. 与其他已确认接待不兼容时，真实事实和衍生限制仍必须保存，并为受到影响的其他接待建立冲突待办；
8. 新增预约同时检查当前实际事实与当前版本衍生限制。

实际清洁或实际休息完成后，可以用对应实际事实提前结束系统推导限制；未经实际记录，不自动假设已经完成。

### 2.4 超时、提前中止与自身排除

- **超时：**实际服务事实延长，整理、床房清洁和美容师必要休息全部从新的实际结束时间顺延。若撞到后一单，后一单保留并产生冲突；完整休息仍从超时后的工作结束计算。
- **提前中止：**原计划中实际结束之后尚未发生的服务、整理和休息片段退出有效占用；按实际结束重新生成较早的整理、清洁和休息限制。已经发生的事实不回退。
- **自身排除：**冲突扫描只排除当前事实明确替代的 `planned_allocation_id`，以及同一事实版本生成的衍生限制；不能按整个 `reception_id` 粗略排除，以免漏掉同一接待内部真实的资源错误。

### 2.5 跨日期更正

第一次尝试按“原事实区间、新事实区间、旧衍生限制、预计新衍生限制、接待组全部有效占用”的自然日并集取得日期锁。锁内重算后如出现未持有日期，事务回滚并用扩大后的完整集合重试。

请假或事实变更若使整组接待失效，失效事务同样锁定该接待组全部占用日期，而不只锁触发记录自身的相交日期。

## 3. 微信退款不存在结果

### 3.1 渠道状态

渠道退款分腿至少区分：

| 状态                 | 含义                                         | 是否可释放现金预留和资产冻结 |
| -------------------- | -------------------------------------------- | ---------------------------- |
| `never_submitted`    | 尚未发出任何网络请求                         | 业务取消后可以               |
| `submitting_unknown` | 请求已发出，是否到达渠道未知                 | 不可以                       |
| `accepted`           | 渠道已受理                                   | 不可以                       |
| `succeeded`          | 渠道成功                                     | 按成功路径结算，不是释放     |
| `retry_same_id`      | 查询不存在或可重试失败，等待原参数重试       | 不可以                       |
| `terminal_rejected`  | 有可审计证据证明渠道未受理且不会产生迟到成功 | 可以                         |
| `manual_review`      | 仍无法确定                                   | 不可以                       |

`RESOURCE_NOT_EXISTS` 只能进入 `retry_same_id`，不能进入 `terminal_rejected`。

### 3.2 稳定单号和单飞规则

- 首次批准时生成唯一 `out_refund_no`，并保存金额、币种、原订单、退款原因等规范化参数哈希；
- 所有提交与重试只能使用相同 `out_refund_no` 和相同参数；
- 一个退款分腿同一时刻最多有一个拥有有效租约的提交任务；
- 外部调用可能越过租约继续在网络中，因此新 worker 即使查询不存在也保持预留，并使用同一单号、原参数重试；
- 新 worker 不能创建第二个商户退款单号，也不能先释放资金再重试；
- 迟到的成功通知按 `out_refund_no` 幂等完成原请求。

### 3.3 允许解除限制的条件

只有以下路径可以解除现金预留或恢复充值权益冻结：

1. 请求仍为 `never_submitted`，审批被有权限人员撤销，且数据库证明没有提交任务取得过发送权；
2. 渠道返回已分类并留存原文的确定性“受理前拒绝”，该错误不会转异步成功，状态进入 `terminal_rejected`；
3. 渠道成功后，按成功路径把预留转成已退款并把相应权益转作废。

“查询不存在”、超时、网络断开、旧 worker 租约失效或人工判断都不是释放依据。自动重试达到上限后进入 `manual_review`，资金限制保持。

## 4. 礼品卡退款失败恢复

退款批准时保存不可变的 `refund_origin_snapshot`，包含批准前卡状态、当前持有人、当前赠送批次、资产来源 ID、来源所有人和冻结金额。失败恢复只允许回到这个合法来源，不根据退款完成时的页面状态猜测。

| 批准退款前的事实                  | 处理中保护                                       | 明确失败后的恢复                                                                           |
| --------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| 未自用、未赠送，卡为 `available`  | 卡变 `refund_processing`，无资产来源             | 卡恢复 `available`，持有人不变                                                             |
| 正在赠送且尚未领取                | 冻结卡和当前批次，禁止领取                       | 批次仍未过期则恢复 `in_transfer/pending`；已过期则批次 `expired`、卡恢复发起人 `available` |
| 发卡人本人已自用，卡为 `received` | 卡变 `refund_processing`，冻结发卡人对应资产来源 | 卡恢复 `received`，同一资产来源恢复到发卡人并解除冻结                                      |
| 受赠人已经领取，卡为 `received`   | 卡变 `refund_processing`，冻结受赠人对应资产来源 | 卡恢复 `received`，当前持有人仍为受赠人，同一资产来源恢复到受赠人并解除冻结                |

已领取卡不恢复到赠送中的批次，也不重新回到发卡人 `available`。`asset_sources.origin_gift_card_id` 唯一约束继续防止第二份权益；状态恢复规则保证原有那一份权益回到正确持有人。

退款处理中不允许再次赠送、领取、消费或发起第二笔退款。若明确失败时来源已经出现不一致，进入资金异常待办并保持冻结，不能用创建新来源修复。

## 5. 统一锁协议

### 5.1 外部调用边界

数据库锁内不调用微信。提交退款前持久化任务和稳定参数；外部调用结束后开启新的结果事务。任何需要预约日期锁的任务，都在结果事务开始时重新取得完整锁集合并再次校验租约。

### 5.2 两层全序

同时涉及预约资源、任务和业务记录时，严格按以下顺序：

**第一层：事务级 advisory lock**

1. 门店拓扑共享或独占锁；
2. 门店日期锁，按自然日升序。

**第二层：数据库行和唯一事件**

1. `jobs` 行，仅任务结果事务；
2. 预留或读取唯一 `business_event`，完成幂等键和请求哈希判断；
3. `receptions`；
4. `resource_actual_fact_series`；
5. `gift_cards`；
6. `orders`；
7. `refund_requests`；
8. `payment_transactions`；
9. `asset_accounts`；
10. `asset_sources`；
11. 资产或支付分配；
12. 商品库存；
13. 插入业务流水和审计记录；
14. 条件更新 job 最终状态。

同表多行按 UUID 字节序升序。所有会写相同幂等事件的路径，都在取得下游业务行锁之前预留 `business_event`；唯一性检查即使等待，也不会与已经持有的下游行锁形成反向等待。

任务若等待 advisory lock 或唯一事件导致租约临近或过期，在锁定 job 后用 `clock_timestamp()` 重新校验；失效则不触碰业务行并回滚。

### 5.3 哪些操作需要预约锁

| 操作                                     | 拓扑/日期锁                              |
| ---------------------------------------- | ---------------------------------------- |
| 新建、确认、改期、取消并释放资源         | 需要                                     |
| 请假、培训、午休及实际事实新增或更正     | 需要                                     |
| 过期任务使整组 allocation 失效           | 需要，覆盖整组全部日期                   |
| 仅支付、纯资产退款且不改变接待或资源状态 | 不需要，只按业务行全序                   |
| 退款或取消成功后同时改变接待并释放资源   | 需要，先取得完整预约锁，再进入业务行全序 |

锁日期集合按会被读取、替代、失效或释放的整组记录计算。锁内发现接待组还有其他日期的有效占用时，回滚扩大集合后重试。

### 5.4 修订后的内部任务顺序

奖励发放等内部任务统一为：

```text
取得必要的拓扑/日期 advisory lock（通常奖励任务不需要）
→ 锁 job 并按 clock_timestamp() 校验租约
→ 预留唯一 business_event
→ 按全序锁订单、账户、来源和分配
→ 写奖励来源及流水
→ 条件更新 job 最终状态
→ 任一步失败或 job 更新 0 行则整笔回滚
```

这取代 V3 中“先锁订单、账户、来源，再插入 business_event”的顺序。

## 6. 阶段 0 实现补充

### 6.1 角色授权基线

阶段 0 现在使用真实运营入口：

```text
GET /api/v1/admin/operations/overview
要求权限：operations.overview.read
```

检查顺序：读取并校验员工会话、员工启用状态和撤销时间，再读取该门店角色的权限并集。未登录或会话撤销返回 401；有效会话但无权限返回 403；有权限返回今日工作台阶段数据。

初始管理员脚本为 `store_admin` 角色授予该权限。管理后台“今日工作台”直接调用受保护入口，因此授权不是孤立演示代码。

自动化集成测试使用真实 PostgreSQL 覆盖：

- 未登录返回 401；
- 有效会话但无权限返回 403；
- 具备权限返回 200；
- 会话撤销后返回 401。

### 6.2 根目录环境文件

API、worker、迁移和管理员初始化共同导入配置入口。配置入口使用 Node.js 24 原生 `process.loadEnvFile` 读取仓库根目录 `.env`；Drizzle 迁移生成配置也读取同一文件。不增加 dotenv 依赖。

系统环境已有的同名变量优先，便于 CI 和生产注入安全配置。日常启动只执行已有迁移 `pnpm db:migrate`；只有数据库结构有意变更时才执行 `pnpm db:generate`。

| 用例             | 前置条件                          | 预期结果                                                |
| ---------------- | --------------------------------- | ------------------------------------------------------- |
| 午休覆盖必要休息 | 午休完整覆盖服务后 15 分钟纯休息  | 预约保持有效，不生成冲突                                |
| 培训覆盖必要休息 | 培训覆盖原计划休息区间            | 培训时间不计休息；重新补足，无法补足时按阶段处理        |

| 两人并发更正     | 两名前台携带同一 expectedVersion  | 仅一人成功，另一人得到 `FACT_VERSION_CHANGED`           |
| 跨日事实更正     | 原事实当日，新事实延长至次日      | 锁覆盖原、新和整组日期；范围不足则回滚补锁              |
| 旧退款延迟到达   | 旧请求在途，新 worker 查询不存在  | 保持预留，以相同单号参数重试；迟到成功只能完成原请求    |
| 已领取卡退款失败 | 权益在受赠人来源中被冻结          | 卡恢复 received，原受赠人来源解除冻结，不回到发卡人卡包 |
| 授权不足         | 有效员工会话但角色无工作台权限    | 返回 403                                                |
| 会话撤销         | 原会话已写 revoked_at             | 返回 401                                                |
| 根目录环境复现   | 干净终端，仅按 README 创建 `.env` | 迁移、初始化、API 和 worker 均能读取配置并启动          |

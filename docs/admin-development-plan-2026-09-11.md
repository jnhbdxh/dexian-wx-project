# 得闲 SPA 管理后台开发方案

日期：2026-09-11，2026-09-12 更新实施状态。版本：持续交付稿。当前固定路线为先收口共同基线，再完成基础资料、排班和预约经营闭环，之后建设资金及独立商业模块；功能完成与上线验收分别提供证据。

## 1. 已确认范围与依据

- 本任务负责管理后台页面及配套服务端接口；另一位同事负责小程序功能开发。
- 用户已确认另有同事同时修改管理端，具体边界将后续划分；下文负责人均为建议，不代表整个 `apps/admin` 已独占交接。
- 用户已确认按建议顺序推进：先基础资料、基础排班和预约接待闭环，再推进资金、商品与会员；暂无硬性日期。
- 支付、短信和微信接入的现有代码先由本任务盘点，负责人和接手范围在交接后确认。
- 业务依据为 `PRODUCT.md`、`docs/decision-log.md`、V6 及其沿用的历史设计章节；完整需求以原始产品文档逐项核对。交接文件用于了解背景，历史任务角色不代替本次授权。
- 延续 Vue 3、Element Plus、Fastify、TypeScript、PostgreSQL 和现有模块化单体结构。
- 界面以运营动作组织：处理对象、当前状态、操作影响和下一步必须清楚，关键操作能核实结果。

## 3. 建议协作约定

### 3.1 责任划分

| 区域                                     | 建议负责人                 | 约定                                                       |
| ---------------------------------------- | -------------------------- | ---------------------------------------------------------- |
| `apps/admin`                             | 本任务                     | 管理后台页面、路由、交互及页面测试                         |
| `apps/miniprogram`                       | 小程序同事                 | 顾客页面、客户端状态、缓存恢复及小程序测试                 |
| 管理端 API                               | 本任务                     | 管理端鉴权、读取、操作事务及对应测试                       |
| 预约、排班、资源等共用业务服务           | 建议交接后由本任务统一维护 | 小程序同事提供调用需求与联调反馈，两端复用同一套业务判断   |
| 微信登录、短信、支付和 worker            | 归属待交接确认             | 先登记当前负责人、进行中的修改及已验收范围，再决定接手范围 |
| Schema、迁移、权限常量、API 注册和锁文件 | 当前主开发任务为唯一整合人 | 两方不同时生成迁移或改写同一共享入口                       |

### 3.2 工作目录与接口

1. 先盘点现有变更并确认各自归属，形成可复现的共同基线，保留原工作成果。
2. 建议使用同仓库独立 worktree 和分支，如 `codex/admin-operations`；小程序分支由同事管理。共同基线未整理前，先推进方案与独立的只读功能，不迁移他人未提交文件。
3. 各工作目录使用不同服务端口、独立开发与测试数据库；避免一方测试清理另一方联调数据。
4. 每个接口先写明请求、响应、状态、错误码、权限、重复提交及结果未知时的处理示例，再分别实现和联调。
5. 优先兼容现有接口；确需改变字段或状态时，提前记录两端影响并同步发布。不能只改后台导致小程序无法理解新状态。
6. 数据库迁移按共同最新基线顺序生成，由整合人检查序号、快照和 journal。已发布迁移不修改，特别遵守现有支付迁移边界。
7. 按业务阶段提交精确文件，记录测试与已知限制；共享文件的混合变更须先拆分核对。

## 4. 实施顺序与验收目标

每阶段交付页面、真实接口、必要迁移、权限、关键回归和验收说明；阶段较大时继续按下列子项拆分。资金相关未决规则只影响相应阶段，不阻塞无关功能。

### 阶段 0：交接与开发基线

- 核对未提交代码归属、现有运行环境、测试数据库和支付线负责人。
- 对照原始需求建立后台功能清单，区分已实现、待验收、待开发和业务待定。
- 固定接口约定、共享文件负责人及独立工作目录方案。
- 验收：可重现当前登录、预约确认、请假和异常支付入口；记录真实运行结果及未通过项。

### 阶段 1：后台导航、预约查询和日历

当前状态：1A 接待查询／详情和 1B 资源日历已通过代码与前端运行时复核；接待页公共组件真实接入、浏览器 200% 缩放、真实账号及小程序跨端链路仍分别待验收。

- 整理统一导航与当前员工信息，已有登录和权限行为保持一致。
- 1A 增加接待列表和详情，按服务日期、状态、美容师、完整接待号查询并分页；联系方式按实际已验证数据脱敏展示。手机号搜索和完整号码读取须在权限及联系人数据切片另行验收。
- 阶段 1A 为接待列表与详情；阶段 1B 单独增加按美容师查看的日预约时间轴及房间床位占用。1A 完成不代表阶段 1 全部完成。
- 详情聚合预约信息、资源、确认截止、冲突与已有支付状态，内部请假原因不进入顾客接口。
- 验收：前台能定位一条待确认、已确认或失效预约，了解当前状态并进入已有合法操作；小程序历史与详情接口保持兼容。
- 此阶段主要新增读取能力，可在后续经营配置未齐全时先交付。

### 阶段 2：基础资料可维护

当前状态：2A-1 预约政策和 2A-2 动态确认期限已通过定点代码与运行时复核。2B-1 契约已冻结，共同基线已收口；第一阶段 `0010` 名称快照兼容实现已完成、待独立发布验收，第二阶段回填收紧及门店默认时长、服务项目和美容师技能的不可变草稿、预览、发布及历史尚未实施。美容师和房床完整维护另行切片。

- 门店：营业信息、联系信息、默认准备、整理、清洁和休息时长等既有业务配置。
- 服务项目：价格、服务时长、启停及可继承的项目规则；明确显示未配置和显式零值。
- 美容师：资料、启停、服务技能及最低休息要求。
- 房间床位：房间、床位归属、启停与已有预约影响校验；按已确认规则自动安排房间床位。
- 基础资料缺项有可定位的修正入口；资源停用、配置变更保护历史快照，并处理未来预约影响。
- 验收：运营无需修改数据库即可录入一套完整资源配置，小程序读取目录并完成真实可约查询；改价格或时长不改写历史预约。

### 阶段 3：基础排班与限制管理

- 第一小段实现按日或周维护班次、餐休和培训，支持发布前冲突检查。
- 第二小段交付原需求中的周期模板、复制与周期补班，保留人工修改保护。这些属于必交付内容，单独验收，不以重复录入频率决定是否实现。
- 将现有请假登记纳入排班流程，补齐请假记录查询。
- 单独实现有权限、有原因、有记录的请假更正或撤销；撤销不自动恢复已失效申请，不复活已取消接待。
- 设备故障等真实不可用事实按既有设计单独登记，不能套用普通计划发布规则。
- 验收：发布班次不会覆盖请假；普通改班、培训或餐休变动存在未解决冲突时不能发布；真实请假或故障如实生效并返回影响。

### 阶段 4：预约接待与冲突处理闭环

- 分步实现拒绝待确认申请、现场接待录入、原子改期、经人工确认更换美容师、取消接待。
- 现场接待复用技能、可用性、资源分配和报价规则，可不绑定会员，不因手填手机号自动合并会员资产。
- 改期和换人先查询候选及变更影响，再在事务中验证和提交；失败时保留原安排。
- 冲突详情直接进入相应业务操作。操作完成后重新检查冲突依据，确实不再冲突时记录解除原因和关联事件。
- 所有已创建订单或支付交易的接待均按第 8 节矩阵处理改期和取消，包括尚未支付、处理中与结果未知。相关入口依服务端检查限制，不能仅检查是否已支付。
- 验收：请假影响已确认预约后，前台可联系顾客并通过合法动作完成处理；重复提交不重复生效，两人同时操作有明确版本冲突反馈。

### 阶段 5：到店与实际服务

- 到店、开始服务、记录实际结束、中途结束、完成核实。
- 记录实际整理、清洁和休息完成情况，并支持有原因的事实更正与历史查询。
- 根据预约保存的规则快照计算实际超时或提前结束后的占用、整理、清洁和必要休息。
- 实际事实与原计划分别保存，实际超时造成下一单冲突时保留事实和下一单承诺，产生待处理事项。
- 验收：到达预计结束时间不会自动认定服务完成；真实超时可保存；并发更正只保留一个有效版本；服务完成不自动等同到账。

### 阶段 6：交易、收款、核销与退款

- 先接手核对已有微信支付、主动查单、worker、异常支付复核和迁移代码的实际完成度。
- 建立订单查询、收款状态、消费结算和来源流水；展示金额、来源、处理人及时间。
- 分别实现充值方案、来源账户、余额核销、奖励金核销及对账。
- 本阶段交付服务退款、充值退余及共用资金恢复基础，明确原实付可退额度、权益冻结、渠道结果未知和恢复流程。商品退款随阶段 7 商品履约验收；礼品卡退款随阶段 7 卡片生命周期验收。
- 充值按已记录规则处理，例如付 95 元入 100 元余额；后续退款算法必须使用确认的规则版本，不自行推断。
- 验收：重复通知只入账一次；并发扣款不透支；未知结果保留核实入口；取消接待、退款成功和服务完成各自独立。

### 阶段 7：商品、礼品卡、会员与运营配置

- 商品：资料、SKU、库存调整、订单、到店领取核销、退货、商品退款和实际返库；依赖阶段 6 的支付退款基础。
- 礼品卡：配置、销售与使用记录、自用、赠送领取、超时退回、礼品卡退款及异常处理；核心状态与小程序卡包同步，依赖资金与来源冻结基础。
- 顾客与会员：查询资料、接待订单历史、账户流水和权益，控制敏感信息与修改权限。
- 营销：会员权益、邀请、评价、奖励规则和回退，所有奖励追溯实际消费或结算事件。
- 门店内容：在原需求核对后提供必要的营业资料、项目展示等运营配置，发布内容与小程序共用。
- 验收：重复领取不重复核销；退款不自动代表商品返库；卡片领取与退款竞争只产生一个有效去向；奖励发放与回退可追溯。

### 阶段 8：运营交接与上线验收

- 员工与角色维护、授权变更、审计查询随各阶段逐步实现，本阶段做完整复核。
- 完成营业数据初始化、关键链路联调、异常任务监控、备份恢复与迁移演练。
- 用真实门店资料、正式配置及微信/短信渠道验证业务，不将测试参数作为生产默认值。
- 按原始需求验收编号建立对应证据和遗留事项，提供运营操作说明。
- 验收：典型营业日从配置、预约、到店、服务、结算到异常处理可实际操作；生产渠道与发布条件逐项具备。

## 5. 首批推荐交付与具体起点

首批建议覆盖阶段 0—4，形成“配置可维护、排班可发布、预约可查询和处理、冲突可跟进”的后台基础。涉及已支付预约的操作须同时具备明确的资金后续处理能力；该首批范围不等于完整营业或生产上线条件。

第一个开发切片建议是“后台接待查询与详情”：

1. 在现有预约模块基础上补充门店隔离的管理端接待查询与详情读取；具体路径以接口约定定稿为准。
2. 返回真实预约状态、资源、版本、确认截止及操作者权限，不向前台展示无法执行的操作。
3. 新增列表、筛选、详情和现有确认动作入口，统一分页、空状态、错误反馈和登录恢复。
4. 覆盖门店越权、分页稳定性、失效状态、权限、确认后刷新以及已有顾客接口兼容回归。
5. 提供页面运行截图与一条“小程序创建 → 后台查询 → 后台确认 → 小程序读取结果”的联调记录。

## 6. 每个阶段的质量要求

- 权限在服务端验证；管理写操作遵循现有会话、CSRF、幂等及版本约定。
- 接待与资源变化沿用共同锁协议和事务，外部微信调用不放在数据库锁内等待。
- 网络结果未知时保留原请求用于核实；不把未知当作未成功而重新创建业务。
- 关键业务自动化覆盖并发、跨日、超时、重试、回滚及历史快照；界面验证聚焦真实操作结果。
- 使用项目现有格式检查、类型检查、测试和构建命令；只执行与变更相关的必要回归，再完成规定的整合检查。
- 数据库测试实际执行结果单独记录，跳过不算通过；已有基线故障与本次新增故障区分记录。
- 页面完成需有浏览器操作验证；渠道模拟通过与真实微信/短信联调通过分别记录。

## 7. 仍需确认的信息

首批交付顺序已确认，暂无硬性上线日期。当前待交接的是支付、短信及微信接入代码的负责人和接手范围；先完成盘点，不将该待定项扩大为全部后台开发的阻塞。

进入相应阶段前再集中核对：

- 基础资料与排班前：真实营业时间、前台可处理线上申请的时段、房间床位清单、项目价格时长、美容师技能、班次和休息规则。
- 预约操作前：拒绝和取消条件、收费或退款衔接、人工换人的顾客确认方式、迟到和未到店处理；已有决定不重复询问。
- 权限维护前：前台、店长、排班人员、财务的具体可操作范围。
- 资金权益前：收款时点与截止、线下收款方式、充值退余、礼品卡部分使用、奖励回退、领取期限、商品分批领取和返库规则；原需求与决策已有答案的直接沿用。

工作量在共同基线、首批范围和未决规则明确后按切片估算。真实渠道审批和外部配置等待单独列出，不将其混入纯开发工期承诺。

## 8. 改期与取消的支付状态矩阵（阶段 4 开工门槛）

以下是分段实现约束；涉及收费和退款的经营条件仍使用确认的规则。阶段 4A 先支持无订单、无支付交易的安排变更；阶段 4B 在支付交接和本矩阵联调通过后才开放其余组合。

| 订单／支付状态                 | 改期、换人、换床房或项目变化                                                       | 取消                                                                           | 原单、通知与后续处理                                                                         |
| ------------------------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| 无订单且无支付交易             | 4A 可开放；重新计算安排和报价，确认影响后原子切换                                  | 4A 可开放；按合法状态释放该接待资源                                            | 与首次创建支付使用共同接待版本与锁序，锁内复核确实无订单；重复请求返回原结果                 |
| 已建订单，无支付交易           | 4A 阻止，保留原安排；4B 设计明确的订单作废／报价版本替代后开放                     | 4A 阻止，转交易跟进；4B 先固化不可再支付状态，再取消                           | 不能更新订单快照假装是原报价；旧收款截止不得沿用到新安排                                     |
| 待支付（已有交易或预支付凭据） | 4A 阻止；4B 暂停新支付发起、主动查单及必要关单，取得渠道明确终态后重新评估         | 同左；只有确认关闭且无到账事实时进入未付取消流程                               | 原商户单号和凭据保留审计，停止对旧交易发新支付参数；关单或查询未知时继续保留原安排和跟进记录 |
| 处理中／结果未知／人工复核     | 禁止直接变更，明确提示先核实对应支付单                                             | 禁止直接取消释放后重新收款，先进入查单或人工跟进                               | 复用原商户单号和恢复任务，不能新建交易绕过未知状态；失败未必表示渠道未扣款                   |
| 已支付                         | 4B：同价变更保留已付来源；差价变更必须具备明确补差或退款订单流程，未实现则限制入口 | 4B：取消与退款分别留痕，生成可追踪退款事项；实际退款完成前仍显示对应处理中状态 | 不改写已付订单快照；不隐式重扣。补差、收费、退款范围未确认时保持入口受限                     |
| 退款处理中／结果未知           | 禁止会改变退款依据或被冻结权益的变更，先核实退款                                   | 重复取消只回显既有接待及退款进度，不重复退款                                   | 持续冻结相关权益；沿用原退款单号，终态后再决定允许动作                                       |

共同要求：

- 接待变更、支付创建、worker 查关单与渠道通知采用同一接待／订单版本和锁约定，外部调用在事务外，回写时重新验证版本。
- 渠道成功通知是独立到账事实，即使晚于关单请求、变更请求、确认截止或取消，也不能丢弃；保留原交易到账记录，禁止复活旧预约或覆盖新安排，转支付异常并指向该接待及原单。
- 4A 被限制的组合必须给出实际支付状态、已有异常支付入口或明确的交易跟进记录；对尚无恢复入口的组合不宣称可完成处理。
- 4B 开发前补充订单替代、晚到通知、关单与成功竞争、原价／差价改期、旧截止、取消与支付创建竞争、重复请求和异常恢复测试。矩阵通过后才扩展入口。

## 9. 预约配置、计时与发布语义

### 阶段 2：配置生命周期与预约入口参数

- 营业日历和前台可确认日历分别维护，支持周规则、指定日期例外、跨日区间、生效时间与范围；可累计区间取两者交集。
- R09 的最远预约日期、最少提前量、开始时间网格分别配置，线上可约查询和创建预占都验证。现场入口只免除顾客提前量和网格，不免除资源与工作时间约束。
- R21 的线上保留时长和现场保留时长分别配置，均有限且大于零；配置草稿不影响可约，发布后形成新版本，旧接待保留创建时配置和明确截止。
- 价格、时长、营业安排、人员启停、技能撤销等变更都有草稿、校验、发布或启用、生效范围与历史版本。普通变更若破坏未来有效预占或已确认安排则禁止发布，并列出需要先处理的记录；历史停用记录仍可查。
- 发布和顾客提交沿用拓扑锁、完整日期锁及配置版本检查；提交取得旧候选而配置已经发布时重新校验，失败不产生部分记录。不能只写页面而不接入预约判断。

### 阶段 3：日期整体发布与自动补班

- 以同门店、同排班日期作为整体版本和发布边界。原有效版与新草稿分开保存，完整检查后一次切换；失败保留旧版与草稿，不出现部分人员已发布。
- 明确记录未排班、人工休息、人工草稿及已发布状态。无排班不开放；明确休息不是缺失记录。
- 模板支持周或多周周期、循环起点和生效范围；首次生成与定期任务只补缺，覆盖开放范围和任务间隔余量，不覆盖人工草稿、人工修改、休息或已发布安排，不擅自发布人工草稿。
- 跨日班次归属开始日期，检查相邻日期；请假事实仍单独有效。R14 的最低在岗及技能人数不足生成缺岗告警，正在服务的人计入在岗；强约束另行配置。

### 阶段 4：两类计时与单笔期限

- 线上累计营业且前台可处理时间，闭店提交从下一可处理区间累计；现场按连续自然时间计时。
- 最终截止不超过整组最早准备／工作开始。该上限前不存在有效可处理窗口时拒绝线上申请；即时接待使用直接确认入口。
- 单笔期限修改是独立授权动作，必须在尚未到期时提交并记录原因、原新期限和规则；不能越过最早工作开始，不能复活已到期记录。与确认、撤回、到期共用竞争规则。
- 验收覆盖跨闭店、多段累计、跨日、无可处理窗口、配置变化不改旧期限、最后一刻竞争。当前固定十分钟自然时间仅为现有切片，不算 R21—R23 完成。

## 11. 通知、交班与具体权限

- 阶段 3 交付缺岗、生成失败和发布失败的日期／人员／原因定位及重试；阶段 4 交付预约确认、拒绝、变更和到期的消息发送结果、失败记录、重试及人工联系记录。消息失败不回滚业务成功。
- 阶段 1B 展示未完成事项，阶段 4 补齐交班记录和责任人，保留未来、跨日接待、待确认、冲突及故障；阶段 6—7 将未核实支付、退款和待交付纳入交班；阶段 8 完整验收 AT24—25、Q04、Q07。
- 首个查询切片沿用 `operations.overview.read` 查看本店接待及必要资源信息；联系方式只返回当前已验证号码的脱敏值，没有数据则明确显示未绑定，不提供完整号码。内部请假原因不在新查询接口返回，冲突展示业务影响并进入现有请假工作台；该工作台原权限边界另在阶段 3 复核。
- 确认继续要求 `receptions.confirm`；资金状态及异常入口要求 `payments.review.read`，重新查单要求 `payments.review.reconcile`。无该权限不返回支付明细，不能把无权限显示成未付款。
- 阶段 2—4 为资料发布、排班发布、请假登记／撤销、查看完整联系方式、查看内部原因、期限修改、拒绝、撤回、改期、换资源、取消分别建立权限映射。完整敏感信息读取记录访问依据，业务写入保存操作人、时间、原因与前后版本。
- 阶段 6—7 将核销、退款审批／执行、库存调整和规则发布分权，审计不可被业务页面删除；新增动作未配置权限默认拒绝。

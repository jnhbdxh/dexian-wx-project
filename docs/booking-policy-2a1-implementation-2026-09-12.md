## 2. 冻结范围的实现

### 数据与发布生命周期

- 新增门店预约创建模式：`legacy`、`paused_for_policy_activation`、`policy_enforced`。
- 草稿与发布版本均为不可变修订；发布版本直接记录来源草稿修订、基础发布版本、发布人、原因和时间。
- 草稿保存、首次暂停和发布操作保存完整原请求及请求哈希。重放顺序为：身份与权限校验、查找原事件、比对请求哈希、再返回原成功、确定失败或处理中状态；确定的 4xx 结果不会因后续业务状态变化而改成成功。
- 首次发布必须先暂停新预占。暂停事务取得门店排他锁，并等待已经取得共享锁的在途预占结束；发布在同一门店锁内重新检查未来有效待确认／已确认接待，成功后原子写入首版政策并启用强校验。
- 营业区间缩短、闭店或自然日例外截断影响未来有效接待时阻止发布并返回明细；提前量、开始网格和最远日期只约束新申请。

### 营业规则与预约入口

- 周规则按开始自然日展开；日期例外按实际自然日覆盖。闭店例外会截断前一日延续部分，替代区间采用相同规则。
- 未发布政策时，公开时刻接口返回 `dateRange: null` 和 `starts: []`，不返回临时经营默认值。
- 已发布后由服务端返回门店时区下的首尾可选日期、政策版本、所查日期状态及精确 ISO 开始时刻；传项目时同时排除完整服务区间放不下的时刻。
- 可约查询和创建预占均校验日期范围、提前量、开始网格及完整服务区间；已成功但响应丢失的原幂等请求仍优先返回原结果，尚未成功的旧候选在政策版本变化后失败。

### 操作端与顾客端

- 管理端新增 `/booking-policy`：集中展示当前状态、草稿编辑、周区间、日期例外、当前版本差异、未来自然日营业展开、影响预览、首次启用、发布原因、恢复入口和历史版本。
- 发布资格同时绑定草稿修订和编辑器完整内容；编辑后旧预览立即失效，必须另存不可变草稿并重新预览。工作区、编辑器、预览、历史及游标共用身份观察，预览和历史分页另有独立数据请求序号；刷新或身份切换会使在途读取失效，合并前再次核对工作区身份与分页基线，401／403 清除受保护内容。
- 首次启用按“暂停新预约 → 重新加载并预览 → 发布首版”的操作顺序组织；未知结果锁定原请求，跨登录继续使用原员工、门店、草稿、基础版本、原因和幂等键核实。
- 小程序不再生成本地默认日期和时刻，直接使用服务端日期范围与精确时刻；未发布时关闭入口并说明原因。

## 3. 接口与权限

- 公开读取：`GET /api/v1/booking/start-options`。
- 管理工作区、版本和修订读取：`GET /api/v1/admin/booking-policy`、`/versions`、`/versions/:id`、`/draft-revisions/:id`。
- 草稿、预览、首次暂停／恢复和发布：`POST /drafts`、`/preview`、`/activation/pause`、`/activation/resume-legacy`、`/publish`。
- 新增 `booking.policy.read`、`booking.policy.write`、`booking.policy.publish`。迁移只注册权限定义，不自动授权既有角色；新环境可在管理员初始化时授予，既有环境必须明确指定门店 ID 和角色代码执行 `pnpm --filter @dexian/api booking-policy:grant-role`。服务端仍按当前会话、门店、CSRF 和原发起身份逐次校验。

## 4. 首次启用运行步骤

1. 先部署管理能力和强校验代码，门店保持 `legacy`。设置 `BOOKING_POLICY_GRANT_STORE_ID` 和 `BOOKING_POLICY_GRANT_ROLE_CODE` 后执行显式授权，再由获授权人员录入、保存并预览首版草稿。
2. 选择营业低峰执行“暂停新预约”；只暂停新的首次预占，已有预约查询、确认及成功请求核实继续可用。
3. 暂停成功代表此前在途创建已经完成；页面重新读取门店身份和最新数据，并对不可变草稿再次预览。
4. 若出现受影响接待，先退出切换并处理接待；不得强行发布。无影响时填写原因并发布精确草稿修订。
5. 发布事务再次检查基础版本和影响，成功后同时切换到 `policy_enforced`；失败保留原草稿和恢复凭据。
6. 从小程序读取服务端日期范围和时刻，完成真实账号、真机网络及跨端链路验收后再批准上线。

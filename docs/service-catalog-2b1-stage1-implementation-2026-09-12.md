# 阶段 2B-1 第一阶段实现与发布说明

日期：2026-09-12（Asia/Shanghai）

## 本发布版本的边界

本阶段只交付接待项目名称快照的增量结构、创建写入和兼容读取，为后续服务目录改名与版本发布建立历史数据边界。

- 发布包的迁移 journal 只到 `0010_reception_service_name_snapshot`，不得包含 `0011`。
- `0010` 只为 `reception_guests` 增加可空的 `service_item_name_snapshot`，不回填、不增加非空约束。
- 新建接待在已有幂等判断、候选校验和锁定流程之后，从数据库读取项目名称并随顾客明细写入快照。
- 顾客预约、后台接待、今日待确认、资源日历、请假冲突和预约政策影响列表优先读取快照；空快照兼容回退到项目当前名称。
- 本阶段不开放项目改名，不提供服务目录草稿、预览、发布或历史接口。

## 第一阶段部署顺序

1. 从共同基线 `804823b4b736c1a4a4d6456bc9ed242f174de5c5` 构建第一阶段发布版本，确认产物中只有到 `0010` 的迁移。
2. 先执行增量迁移，再滚动升级所有能够创建接待的 API 实例。旧实例可继续在新增的可空字段下运行，但仍可能写入空快照。
3. 确认旧创建实例全部退出，并等待其在途创建请求结束；记录实例版本和切换时间。
4. 核对切换时间之后新建的 `reception_guests` 均有名称快照，并统计过渡期空值。发现新空值时不得进入第二阶段。
5. 在第二个独立发布版本中才允许加入 `0011`，完成过渡期空值回填、遗漏核对及约束收紧；回填名称只能表述为“回填时名称”。
6. `0011` 完成且确认无空值后，才可开放项目改名并取消当前名称回退。

旧版本 API 可在 `0010` 后安全回滚，因为新增字段保持可空；新版本 API 不得回滚到尚未执行 `0010` 的数据库。

## 验收重点

- 新建接待的每条顾客明细均保存当时项目名称。
- 修改项目当前名称后，已保存快照的接待在六类历史读取中仍显示原名称。
- 过渡期空快照仍能读取，不影响已有接待查询、确认、支付或异常恢复。
- 同键成功恢复仍优先返回原业务结果，不因名称查询重新执行业务。
- 本阶段完成不代表浏览器缩放、真实微信身份、真机网络或完整跨端链路验收通过。

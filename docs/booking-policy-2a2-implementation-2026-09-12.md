# 阶段 2A-2 实施记录

记录日期：2026-09-12（Asia/Shanghai）

## 交付结果

本切片实现预约政策 V2 的两项门店级时长配置与前台处理日历，并将线上确认期限接入可约查询和创建预占事务。两项时长均可配置、无业务默认值，接口和管理端的技术范围为 `1–43,200` 分钟。

- `onlineHoldMinutes` 按营业日历与前台处理日历的有效交集累计实际毫秒。
- `onsiteHoldMinutes` 保存、预览、发布并展示，但明确标注为“待现场接待入口接入”。
- 线上截止不晚于整组最早准备开始；若仍有部分有效处理时间则在该边界截断，完全没有有效处理时间时拒绝创建。
- 接待 `confirmationDeadline` 与同组全部有效预占 `expiresAt` 使用同一个事务内计算结果。
- 计算起点、最早准备时间、实际累计毫秒、实际使用的处理分段、截断标志和最终截止写入每位接待顾客的 `rule_snapshot.confirmationHoldComputation`，用于后续核对。

## 兼容与恢复

- 历史政策和候选凭据分别兼容 V1/V2 解码。
- 新草稿保存和发布只接受完整 V2；旧 V1 草稿必须补全后形成新修订。
- 创建预占先按当前顾客、操作类型和幂等键查找原记录，再比较原始候选令牌哈希。成功、处理中和已持久化的确定失败分别重放原结果或状态；只有没有原记录时才执行业务事务。
- 旧 V1 请求若已成功，即使后来发布 V2 政策，仍可同键重放原成功结果；尚未成功的旧候选不能绕过当前 V2 政策。
- 可约候选只保存不可变政策修订、发布版本和线上分钟数。数据库当前时间及动态期限结果只在创建事务内生成，避免查询至提交的时间流逝被误判为候选配置变化。

创建预占接口在当前顾客身份与幂等键格式确认后，先按顾客、操作类型和幂等键锁定并检查业务事件，再比较原始候选令牌哈希。原成功、处理中或确定失败记录均不依赖当前候选验签密钥解码；只有不存在原记录的新请求才解码候选。因此，同键替换为无效候选会返回 `IDEMPOTENCY_KEY_REUSED`，原成功请求在候选验签密钥轮换后仍能返回原结果。

不可约响应新增稳定 `reasonCode`。其中 `BOOKING_CONFIRMATION_WINDOW_UNAVAILABLE` 与 `RESOURCE_UNAVAILABLE` 分开传递；小程序逐个时刻分别显示“无确认处理时段”或“暂无空位”，在没有任何可选时刻时明确提示选择更晚时间。

## 管理端

预约政策页可分别编辑线上、现场时长，以及营业日历、前台处理日历和两类日期例外。保存前要求两个时长都填写有效值；旧 V1 内容不会自动补十分钟或其他默认值。预览同时展示营业区间、原始处理区间和两者实际交集，历史详情保留 V1/V2 对应说明。

已启用的每周营业日、每周处理日和“替代”日期都必须至少包含一个明确区间。管理端会禁用保存并提示补全，API 同时做最终校验，避免运营人员把“已启用但没有区间”误当成正常开放配置。

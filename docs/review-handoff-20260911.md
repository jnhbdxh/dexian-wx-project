### 3.4 资金、卡与商品不能丢失的规则

- “九五折充值”明确为现金付 95 元、余额入 100 元，不是付 100 元赠 5 元，也不是后续消费再次九五折。
- 现金、充值余额、奖励金、贡献值是不同对象。余额必须能追溯资金来源、已用、冻结、可退及退款去向。
- 不允许只修改账户余额而不留流水；流水不可删除，冲正应有对应记录。
- 礼品卡的自用、赠送领取、退款等竞争必须只产生一个有效权益去向；退款应追溯原购买现金来源。
- 竞品“赠送 24 小时无人领取退回卡包”、会员等级比例、注册/邀请奖励等是参考示例，未逐一确认的数值不得直接作为生产承诺。
- 服务退款、商品退款、充值退余、礼品卡退款分别考虑；退款累计不能超过对应原实付可退额度。
- 退款处理中应冻结相关权益，结果未知时不能提前解除冻结或允许重复消费。
- 充值消费后的退款计算不能自行编造比例公式，应依据明确发布的规则版本及来源明细。
- 会员/邀请奖励应基于相应实际完成或结算事件，不应仅因前台确认接待就发放；重复事件不重复发奖，退单需要关联回退。
- 商品价格和库存应在结算时重核；付款成功不等于已经到店交付；重复领取不能重复核销。
- 商品退款不代表自动返库，是否返库取决于真实退回及可售状态。

## 4. 已确认的关键经营与实现决定

### 4.1 房间、床位自动安排：DEC-003

- 顾客只选择门店、项目、时间和美容师，不参与选择房间或床位。
- 自动安排仅涉及房间和床位，不允许顺带推荐或替换美容师。
- 一期适用性模式为 `all_active`：所有合法、已启用房间默认适用所有已启用项目。
- 合法性仍要求同门店、资源类型正确、资源启用、床位真实归属于所选房间。
- 占用、技能、请假、班次和并发冲突是独立校验，不会因“项目适用全部房间”而被跳过。
- 多人底层请求需要寻找完整可行组合，不能使用逐人贪心分配导致 A/B 顺序不同就遗漏可行方案。
- 后续 `only_listed` 扩展应复用统一入口，模式与项目—房间关联分开；“限制列表为空”不能解释成“全部适用”。
- 当前不需要提前建设绑定表、配置页面或通用规则引擎。
- 顾客接口不接收/公开房间、床位内部编号；内部明确指定能力也必须经过相同适用性校验。

### 4.2 预约时间、占用和并发

- 查询只是候选，不是资源承诺；提交时在事务及资源锁内重新校验。
- 预占最多 10 分钟，确认截止不能晚于整组最早准备开始时间。多人不同开始时间按整组最早边界计算。
- 候选通常 5 分钟有效，仍受更早的准备边界约束。锁等待后必须重新读取数据库时间。
- 按“门店拓扑共享锁 → 完整日期集合升序锁 → 后续业务锁”的共同协议执行；整组涉及未锁日期时应回滚、扩锁后重试。
- 日期锁等待上限为 1500ms，最多尝试三次；最终返回 `RESOURCE_BUSY_RETRY`，不能留部分接待、占用或幂等事件。
- 自然过期通过数据库固定状态物化，排斥约束谓词不依赖变化的 `now()`。
- 准备、服务、美容师整理、人员休息、设施清洁分开；美容师休息可与场地清洁并行。
- 时长规则采用“项目配置 → 门店默认 → 美容师最低休息要求”，未配置与显式 `0` 必须区别。
- 预约保存配置版本、最终分钟数和完整规则输入快照，不用后来的配置重算历史。
- 一期同组暂不共享美容师或设施资源；前端多人功能仍关闭，不能把后端支持多个参与者解释为多人产品已完成。

### 4.3 24 小时上限：DEC-002

正常单次接待从最早准备到最晚必要休息结束，整体占用不超过 24 小时；允许跨午夜，必须锁完整日期。实际服务超时属于真实事实，后续事实入口不能因超过该上限拒绝如实记录，应进入冲突处理流程。实际事实入口并未因此自动完成。

### 4.4 真实请假与班次

- 真实请假无论提前或临时登记，保存即生效；未来尚未排班也允许登记。
- 冲突不能阻止真实请假保存，不增加申请审批流程，不自动换人。
- 相交且尚未过期的待确认接待整组变为 `invalidated`，所有资源释放。
- 已自然过期的接待标为 `expired`，不能计入“因请假失效”的数量。
- 已确认接待保留原记录和占用，生成同一请假与同一接待唯一的冲突待办。
- 请假只覆盖必要休息不算工作冲突，不应使接待失效或生成待办。
- 请假、午休和下班可抵扣连续纯休息；培训等工作不能冒充休息。
- 基础班次允许与请假相交并保留完整记录；有效工作区间及可约必须扣除请假。
- 后生成班次不能覆盖、撤销请假；培训、会议、值班等具体工作不能落入请假区间。
- 普通培训、餐休、改班遇到已有冲突，先处理冲突再发布，不套用“真实请假必须生效”的例外。

### 4.5 支付与状态分离：DEC-001

一期单笔交易只采用一种支付来源，不支持混合支付。未来启用混合支付须重新设计拆分扣款、补偿及退款分摊。

接待确认、实际服务、支付交易、商品交付、礼品卡、退款是独立状态体系。服务时间过去不等于已实际完成，前台确认不等于已付款，付款不等于商品已交付，退款不等于库存已返还。

所有对外金额，包括逐人 `quoteCents`，使用整数分的十进制字符串。例如 `"32850"` 显示 `¥328.50`，不要在 JSON 直接传 `BigInt`，不要悄悄丢掉分位。

## 5. 技术基线与工程结构

### 5.1 已沿用的选型

- 微信原生小程序 + TypeScript。
- Fastify 统一 API；Vue 3 管理后台。

## 7. 最新小程序真实预约切片：实现与最后结论

### 7.1 正常链路

1. 加载恢复记录；有未核实请求时，优先恢复原预约，不依赖目录必须成功。
2. 读取真实门店、项目与具备技能的美容师目录。
3. 使用顾客会话查询所选时间可约，后端自动安排合法房间床位。
4. 顾客确认后，提交前重新查询。
5. 新价格或服务时长与原摘要不同时，先更新完整摘要并要求再次确认，不直接创建预占。
6. 即将发送预占前保存原不透明候选、幂等键和预约摘要。
7. 创建成功显示“等待门店确认”和服务端确认截止时间。
8. 网络、服务异常等结果不明确时保留原请求，只能同键核实。

### 7.2 候选与幂等边界

- 候选使用 Node 内置 AES-256-GCM 认证加密，不再是能解码读取内部编号的明文签名载荷。
- 对外白名单响应不公开房间、床位内部编号。
- 尚未成功的旧候选受所属顾客、会话、过期和规则版本校验约束。
- 已成功但响应丢失的请求，原顾客可使用原候选及原幂等键直接重放结果；重新登录、候选自然过期、后续规则变化不能阻断该已成功结果核实。
- 同键换候选/请求仍拒绝，不能借核实发起另一笔预约。
- 不要声称小程序恢复记录已像员工请假记录一样保存并绑定原顾客 ID；当前关键归属保护来自服务端候选所属顾客校验及明确重新登录恢复链路。

### 7.3 本切片四项 P2 及最后追加修复

| 问题                               | 修复后的要求/结果                                       |
| ---------------------------------- | ------------------------------------------------------- |
| 提交前报价或时长变化仍直接下单     | 更新摘要，停在再次确认，不自动 POST                     |
| 401/候选所属账号不一致删除未知记录 | 保留原候选及幂等键，要求回原账号核实                    |
| `onShow` 跨日改写未知/成功预约日期 | 交互锁定时不重置原日期                                  |
| 所有可约查询失败没有可见恢复入口   | 时间区域直接显示错误和重试指引，底部可重新查询          |
| 返回原账号后仍复用缓存 B 会话      | 明确“重新登录原账号并核实”入口，清缓存并强制 `wx.login` |

最后一条的运行时回归：请求先使用 `cached-B`，收到身份异常后保留恢复记录；再次操作执行一次 `wx.login`，后续请求使用 `token-A`。两次 `Idempotency-Key` 完全相同，最终成功后才清理恢复记录。

另做过登录失败与重新载入的补充验证：强制登录失败时不发送新的业务 HTTP 请求，原候选/键继续保留、交互继续锁定；重新初始化仍显示重新登录原账号的核实入口。

### 7.4 当前结论与仍然不能声称完成的内容

上述 P2 的代码和页面交互回归已闭合。本结论不扩大为完整小程序或正式上线通过。

## 12. 下一轮优先事项：真实联调准备与验收

### 12.1 联调不等于上线，先限定目标

建议先做“真实微信身份 + 真实测试 API/数据库 + 单人预约预占 + 后台确认/请假”的受控联调，不夹带真实支付和未评审迁移。

应分别记录四个门槛：代码回归通过、模拟器链路通过、真机链路通过、可正式营业/上线。前一项通过不自动推出后一项。

### 12.2 用户需要准备/核实的材料

| 事项                             | 为什么需要                             | 当前预约是否必须                         |
| -------------------------------- | -------------------------------------- | ---------------------------------------- |
| 正确的小程序账号与真实 AppID     | 确保测试的是得闲实际小程序而非游客模式 | 真实微信身份联调需要                     |
| 服务端可安全配置的 AppSecret     | 后端交换微信登录身份                   | 需要；不要发聊天或提交仓库               |
| 有权限的测试微信账号、测试手机   | 登录、预览/体验版本及账号恢复验证      | 需要，成员权限以控制台实际状态核对       |
| 可达的测试 API 环境              | 手机不能访问电脑自己的 localhost       | 真机需要                                 |
| 测试域名及证书/平台配置权限      | 规范验证安全网络访问及体验流程         | 正式体验链路需核对，开发临时调试不能替代 |
| 门店资料、项目与人员的测试确认值 | 建立可解释的可约和冲突数据             | 可先用标记清楚的测试资料                 |
| 支付商户号、支付证书等           | 真实收款链路                           | 当前预约联调不需要，支付另验             |
| 短信渠道                         | 短信验证码等后续功能                   | 当前微信会话预约链路不以短信为前置条件   |

不应要求用户一次性补齐所有商品、营销和会员参数后才能开始预约联调；先完成本链路必要配置即可。

### 12.3 开发方在联调前应处理的工程事项

1. **确定版本与迁移集合。** 将本轮已评审预约实现整理成可识别的联调版本，列清与支付线共享文件的差异。不直接把当前整个脏工作区上线。
2. **建立隔离测试数据库。** 明确名称、连接和用途，执行该联调版本批准的已有迁移。不要复用真实经营库或向不明连接运行测试。
3. **准备持续存在的联调种子数据。** 单元/集成测试完成后会清理的夹具，不等于操作人员可用的真实联调目录。
4. **配置微信身份。** 小程序私有 AppID 与后端 AppID/AppSecret 一致；核实真实登录没有走开发登录兜底。
5. **配置小程序 API 地址。** 当前 `127.0.0.1:3000` 仅适合本机相应调试；手机上 `127.0.0.1` 是手机自身。环境切换由开发方明确实施，评审方不擅自改。
6. **配置网络与后台会话。** API 监听、端口、防火墙、后台 Origin、Cookie/CSRF 与测试部署一致；不把 PostgreSQL 直接暴露到公网。
7. **验证基础健康。** 存活与数据库就绪、后台登录、目录读取、权限及真实顾客会话正常后再开始业务验收。
8. **保留安全观测。** 记录请求 ID、业务事件和必要数据库证据，日志不打印 AppSecret、完整会话、内部请假原因或其他不必要敏感信息。
9. **约定清理方式。** 只清理明确标识的测试门店/测试数据；保留验收记录后再执行清理，不用全表清空模拟通过。

### 12.4 最小联调数据集

至少准备：

- 一个明确标注的测试门店，使用 `Asia/Shanghai`。
- 一个以上启用项目，包含金额、服务时长、准备/整理/清洁/休息规则及有效版本。
- 两名可用美容师及正确技能；至少两组房间—床位，资源类型、门店和父子关系正确。
- 覆盖未来日期的已发布班次，准备与工作性整理也必须在有效工作区间内。
- 一组“只剩最后一组设施”的竞争数据，以及另一组正常可约数据。
- 有确认接待权限的运营员工；有请假登记权限的运营员工，可为同一受控测试管理员。
- 用于提前请假、跨午夜、临近确认截止的独立场景，避免测试互相占用同一资源时段。

`admin:bootstrap` 只建立门店及管理员/角色等基础内容，不会自动配齐项目、技能、房间床位与发布班次。看到后台能登录，并不等于小程序应该已经有可约结果。

### 12.5 网络和微信平台要求的核对边界

本机模拟器可以先连接本机 API；开发调试中的域名校验选项只能用于明确的开发验证，不能作为正式体验或发布条件的替代。

真机应使用手机实际可达的受控地址；规范体验联调通常需要 HTTPS、可信证书及小程序 request 合法域名等配置。局域网临时调试若使用特殊调试模式，必须明确记录，不得据此宣称正式网络条件通过。

此前尝试抓取微信官方页面未成功，本交接不声称已核实 2026-09-11 当天全部最新平台条件。实际配置时由新对话重新核对官方文档和控制台：

- [微信小程序网络能力](https://developers.weixin.qq.com/miniprogram/dev/framework/ability/network.html)
- [微信小程序登录](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/login.html)

备案、类目、隐私声明、体验成员及公开发布资格应按实际账号和目标环境核对；不要用旧经验截图承诺办理时长或认定已经办妥。

### 12.6 建议按顺序执行的真实链路

| 顺序 | 验收动作                           | 必须观察的结果                                     |
| ---- | ---------------------------------- | -------------------------------------------------- |
| 1    | 清楚标识测试环境，用真实微信登录   | 后端建立正确顾客身份；重复登录不产生错误重复归属   |
| 2    | 加载真实目录、选择项目/美容师/时间 | 数据来自测试库，无设施内部编号，不自动换美容师     |
| 3    | 查看摘要并创建预占                 | 一条 pending 接待、正确明细/资源占用、准确确认截止 |
| 4    | 管理后台查看并确认                 | 同门店有权限员工才能确认，整组转换一次             |
| 5    | 返回顾客侧检查当前支持的反馈       | 不把尚未实现的确认状态自动同步当作已完成           |
| 6    | 候选后更改价格/时长再提交          | 新摘要完整显示，要求再次确认，没有直接按新价下单   |
| 7    | 两个顾客竞争最后设施               | 最多一单成功，失败方无部分数据并有明确恢复指引     |
| 8    | 查询后停用场地或插入冲突           | 提交重新校验并拒绝，不默默换已选美容师             |
| 9    | 真实请假击中 pending / confirmed   | 前者整组失效；后者保持接待及占用并产生唯一冲突     |
| 10   | 锁等待或操作延迟跨过截止           | 使用锁后数据库时间，不能依客户端倒计时确认         |
| 11   | 可约查询全部失败                   | 时间区域和主按钮有明确重试入口                     |
| 12   | 服务端已成功但响应丢失             | 重载页面仍用原候选、原幂等键核实，只存在一笔接待   |
| 13   | 账号不匹配后回原身份核实           | 保留原请求，强制登录后仍同键，不由新账号代办       |
| 14   | 强制登录本身失败并重进页面         | 凭据仍在，不能生成新请求绕过未知结果               |

“断网测试”必须区分请求根本没发出与“服务端已提交、客户端没收到响应”。仅提交前断网不能证明最关键的重复创建防护。身份切换在真实微信环境需使用平台实际支持的账号切换/测试方式；`wx.login` 刷新的是当前微信身份，不是允许顾客在应用里输入任意账号冒充 A。

### 12.7 UI 与操作员验收

- 当前真实接口版本重新截图：首屏、日期时段人员、完整摘要、待确认成功、报价变化、全查询失败、未知核实、重新登录入口。
- 检查 390px 窄屏及至少一部实际手机的滚动、底栏、安全区、内容遮挡和操作连贯性。
- “请选择为你服务的美容师”应清楚；不再出现暗示自动分配美容师的文案。
- 成功明确是待门店确认，不说已经确认或已完成服务。
- 内部资源编号、内部请假原因不面向顾客泄露。
- 运营页面保存请假前说明立即生效、待确认失效、已确认需人工跟进；按钮动作与实际结果一致。
- 对未知结果应说“结果待核实”，不是“预约失败，请重新预约”。
